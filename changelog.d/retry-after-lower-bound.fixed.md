- A provider's `retry-after` is now a lower bound inside one call too, on every adapter. A stated wait that fits the schedule's `maxRetryDelayMs`, one equal to it included, is waited out in full. A longer one is no longer retried before it elapses: the call ends and the classified error carries `retryAfterMs` intact, so the caller can pace the next call. As with any error Membrane doesn't retry, `hooks.onError` isn't called for it. A `retryAfterMs` that is not a finite number, which only a custom adapter can state (the readers ignore one), ends the call the same way. This holds on `complete()` and on the callback `stream()` pre-emission retry, for the base and the overload schedules. So a 120 s `retry-after` under the default 30 s cap ends the call with the wait intact, where a clamp to the cap would have retried after at most 30 s.
- Retry waits longer than one timer can represent (2^31-1 ms, about 24.8 days, reachable only through a configured `maxRetryDelayMs`) are taken in steps instead of firing almost at once, and remain abort-aware.
