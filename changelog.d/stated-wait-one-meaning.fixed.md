- Every adapter reads a provider's stated wait from `retry-after-ms` before `retry-after` at the shared HTTP boundary, through one exported reader, `statedWaitFromHeaders`. A fetch-based adapter whose provider stated its wait only in milliseconds used to retry on Membrane's own backoff, inside the wait.
- A stated wait has one meaning wherever it is read: a header, an error body or an SSE error frame. In a body or a frame, `retry_after_ms` and `retryAfterMs` state milliseconds, and `retry_after`, `retryAfter` and Google's `retryDelay` (`'21s'`) state seconds, each as a number or a decimal string, the form a header's value takes too (a hex or exponent string states nothing anywhere). A wait below zero is over (0), so a 429 stating `retry_after_ms: -1000` (or `"-1000"`) retries on the backoff, as it did before stated waits could end a call. A `retry-after` header can also state an HTTP-date, and one already past is 0 too; a date is a header form, so a body or frame field holding one states nothing. Neither does a value that is not a finite number, and the next field is read instead. A wait beyond `maxRetryDelayMs` ends the call with `retryAfterMs` intact, and so does a `retryAfterMs` that is not a finite number, which only a custom adapter can state. A wait stated only in prose ("retry after 30 seconds") is read from the provider's own message, never from the rest of a body, which can echo the request; a body that states it anywhere else retries on the backoff.
  - Verified with scripted fetch through the real adapters; no live provider calls.
