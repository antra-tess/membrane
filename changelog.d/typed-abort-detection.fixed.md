- Abort detection is typed at every boundary: a cancellation is recognised only by type — a `DOMException` whose name is `AbortError`, an `Error` whose `name` is `AbortError`, a membrane `abort` error, or the Anthropic SDK's `APIUserAbortError` — never by reading the message. An error whose message merely contained "abort" — a host tool failing with "...aborted...", a provider mentioning idle-connection aborts — used to resolve the whole turn as `AbortedResponse{reason:'user'}`, destroying the real error and telling the caller the human cancelled; it now throws with its classification and raw request intact.
- The Anthropic adapter's error boundary no longer treats a plain `Error` whose message is exactly `Request was aborted.` as a cancellation. That was the last place the laundering survived: any caller — a tool, a proxy, a wrapped upstream failure — can produce that exact string, and it was converted into a user cancellation even though nothing about its type said abort. The SSE idle watchdog the check was added for never reached it, since the stream catch throws its own typed timeout first. Such an error now surfaces as an ordinary unclassified error with its message and raw request intact.
- Verified live: an in-flight Anthropic request (`claude-haiku-4-5-20251001`) cancelled through its `AbortController` is still classified `abort` at the adapter boundary, while a plain `Error` carrying the SDK's exact abort text classifies as `unknown`. Mock-only: the `DOMException`, `name`-based and membrane-`abort` shapes, and every non-Anthropic adapter (all of which reach the same typed check through raw `fetch`).
