- The two OpenAI adapters read a prompt-cache write into `usage.cacheCreationTokens`: `OpenAIResponsesAPIAdapter` from `usage.input_tokens_details.cache_write_tokens`, `OpenAIAdapter` (Chat Completions) from `usage.prompt_tokens_details.cache_write_tokens`. Under the cache-inclusive normalization the written tokens leave `inputTokens` and are priced on their own: every built-in OpenAI row carries `cacheWritePerMillion` — 1.25× input from GPT-5.6 on where OpenAI's page lists a write price (the guide's 30-minute rate), and the input rate where it lists none: GPT-5.5 and earlier, and `gpt-6-astra-law`, which gets its own row so the prefix rule no longer gives it `gpt-6-astra`'s premium. The Responses API's 12-hour writes (`cache_write_tokens_details.ttl_12h_tokens`) ride the long-TTL slot, `cacheCreation1hTokens`, whose docs now name both TTLs, and the four GPT-5.6/GPT-6 rows price them at 2.5× input (`cacheWrite1hPerMillion`); Chat Completions reports no TTL split, so its writes are all priced at the 30-minute rate. For a call through either adapter priced by a built-in row, `estimatedCost.cacheWrite` is now a number where it was undefined: the writes' cost, or 0 when the provider reported no write count — `calculateCost`'s rule for any row with a rate, as for reads. Before, the field was not read, a write was counted and priced as ordinary input, and the GPT-5.6+ premium was missing from `estimatedCost`.
- A GPT-5.6 id the table has no row for (`gpt-5.6` itself, or a variant) has a `pricing: null` row, so a request for it is unpriced and warns rather than priced by the `gpt-5` row at a tenth of its rates. When such an id is the *served* model of a request for a priced one, `resolvePricing` still falls back to the requested model's row, as it does for every `null` row (#276).
