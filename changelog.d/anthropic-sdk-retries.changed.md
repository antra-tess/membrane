- **`AnthropicAdapter`:** the SDK beneath it no longer retries on its own, so Membrane's retry policy is the only retry policy inside a call, as on every fetch-based adapter. `@anthropic-ai/sdk` defaults to two retries of 408, 409, 429, 5xx and connection failures, made before Membrane saw the error. It replaced a stated `retry-after` of 60 s or more with a backoff of about a second, slept through a shorter wait beyond `maxRetryDelayMs`, and multiplied the documented attempt counts (the five-attempt 429 floor, the overload schedule's seven) by up to three.
  - **What callers see:** an error that Membrane's policy does not retry now reaches the caller from its first request, where the SDK used to try twice more and a transient failure could pass unseen. Under the default `maxRetries: 0` that is a 5xx other than 529, a 408, or a connection failure on `complete()`; set `retry.maxRetries` to retry those on Membrane's schedule. Callback `stream()` retries only rate limits and overloads before output, so on `stream()` those errors reach the caller from the first request under any configuration. A 409 is classified as a non-retryable `invalid_request`, so no configuration retries it.
  - **Cache keepalive:** a poke is one request as well. A poke the provider refuses reports one error receipt and counts toward `maxConsecutiveErrors` at once, where the SDK used to retry it, including inside a rate limit's stated wait.
  - **Unchanged:** rate limits and overloads still retry by default on both paths; the credential resolver's single refresh after a 401 still happens inside one request, and a resolver failure still surfaces as the original error.
  - Verified with scripted fetch through the real SDK on a fake clock; no live provider calls.
